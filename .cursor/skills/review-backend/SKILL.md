# Backend Review Agent

## Scope

This review covers:
1. **Database** — schema correctness, migration hygiene, JSONB vs relational trade-offs
2. **Security / Auth** — RLS policies, RBAC role enforcement, anon access
3. **Services** — `supabaseSync.ts`, `jira.ts`, `nagerHolidays.ts`

## How to run this review

Work through each section below. For each finding, rate it:
- 🔴 **Critical** — security risk or data-loss risk; fix immediately
- 🟡 **Improvement** — best-practice gap; fix before next release
- 🟢 **Nice to have** — optional enhancement

---

## 1. Database schema review

Read these files:
- `supabase/schema.sql`
- `supabase/migrations/` (all `.sql` files, newest first)

Check for:
- [ ] All tables have RLS enabled (no `FOR ALL USING (true)` remaining after migration 009)
- [ ] All entity tables have `created_at` and `updated_at` columns
- [ ] JSONB columns are justified (phases/assignments nesting is acceptable; scalar filterable fields should be typed columns)
- [ ] All migrations are idempotent (`IF NOT EXISTS`, `ON CONFLICT DO NOTHING`)
- [ ] No dangling FK references or missing indexes on FK columns
- [ ] `text` PKs generated by the app (nanoid) — document this in schema comments

Known issues to verify are fixed:
- Migration 002 created `team_members` with `role text` (stores role name, not FK) — intentional, but add a comment
- `projects.phases` stored as JSONB — acceptable for single-tenant; note it prevents per-phase queries

---

## 2. RLS / RBAC review

Read: `supabase/migrations/009_security_auth_rbac.sql`

Check for:
- [ ] `anon` role has no SELECT/INSERT/UPDATE/DELETE on any app table
- [ ] The four roles (`system_admin`, `it_manager`, `team_lead`, `stakeholder`) have differentiated write policies (not just `FOR ALL` for all authenticated users)
- [ ] No policy bypasses `auth.uid()` check
- [ ] `user_roles` self-referential policy (admin reads/writes) doesn't create infinite recursion
- [ ] Frontend: is `user_roles` surfaced in the app? If not, note it as a gap.

Recommended improvement:
```sql
-- Replace repeated subquery with a SECURITY DEFINER helper
CREATE OR REPLACE FUNCTION is_role(r text) RETURNS boolean
  LANGUAGE sql SECURITY DEFINER STABLE
  AS $$ SELECT EXISTS (SELECT 1 FROM user_roles WHERE user_id = auth.uid() AND role = r) $$;
```

## 3. supabaseSync.ts review

Read: `frontend/src/services/supabaseSync.ts`

Check for:
- [ ] `DEFAULT_SETTINGS` and `DEFAULT_JIRA_SETTINGS` match the defaults in `appStore.ts` (drift = silent data loss)
- [ ] All `upsert` calls include `{ onConflict: 'id' }` and the PK in every row
- [ ] `loadFromSupabase` uses `Promise.all` for parallel reads (no sequential awaits)
- [ ] Raw Supabase errors are caught and mapped to user-friendly strings before `setSyncStatus('error', msg)`
- [ ] Debounce interval is ≥ 1000 ms (currently 1500 ms — do not lower)
- [ ] New tables added since migration 017 are included in both `loadFromSupabase` and `saveToSupabase`

---

## 4. jira.ts review

Read: `frontend/src/services/jira.ts`

Check for:
- [ ] API token is never logged (even partially)
- [ ] `fetch` calls have timeout / `AbortController` (currently missing — 🟡)
- [ ] Custom field IDs (`customfield_10014`, `customfield_10016`, etc.) are noted as Jira-instance-specific
- [ ] Error responses from Jira API are caught and surfaced as structured errors (not raw JSON)
- [ ] No sensitive data (token, email) written to `console.log` in production builds

Recommended addition:
```typescript
function fetchWithTimeout(url: string, init: RequestInit, ms = 15_000) {
  const ctrl = new AbortController();
  const id = setTimeout(() => ctrl.abort(), ms);
  return fetch(url, { ...init, signal: ctrl.signal }).finally(() => clearTimeout(id));
}
```
